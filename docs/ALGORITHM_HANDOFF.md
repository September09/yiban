# 忆伴｜记忆检索算法协作任务书

版本：v1.0 · 2026-11-10 · 状态：待实施与共同确认

适用项目：yiban-github。依据本地已核对的 920513f 版本编写；文中“现有”表示已存在，“拟新增”表示本次任务建议，不表示功能已经完成。接手时以实际代码为准，不假定远端已经同步。

## 1. 这次要解决什么

让家庭、团队成员用自然的说法找回共同记忆：换一种表达也能找到，有记录时给出依据，没有记录时明确说明，不串到其他人或其他空间的资料。

第一阶段聚焦“共同记忆检索增强＋效果评测”。保留现有 SQLite、成员权限、原文依据和语音确认流程，不要求训练一个新大模型。

虚构示例：已保存“10 月团队在植物园组织自然观察活动，李老师负责讲解”。用户问“上次大家一起看植物，是谁带我们讲的？”，系统应找到对应记忆，回答讲解者并展示记录来源；资料中没有活动经费时，问“那次花了多少钱？”应说明没有相关记录。

完成的标志：有可运行模块、有接入演示、有同一测试集上的前后对比，且现有权限、数据和语音确认行为没有退步。

## 2. 项目已有能力与需要补足的部分

| 方面 | 当前已实现 | 本次补足 |
|---|---|---|
| 记忆存储 | SQLite 保存个人及共同记忆；共同记忆具有成员权限、可见范围和修改权限 | 在原存储上增加可重建的检索索引，不替换事实主库 |
| 检索 | 按相邻两个字的重合程度选取记录；共同记忆还按状态排序 | 同义表达、别称、相关性门槛与无答案判断，比较混合检索效果 |
| 上下文 | 最多选择 8 条、正文累计约 2200 字符 | 先保证相关，再保留现有预算；初期不要同时改变大模型与上下文长度 |
| 依据与状态 | 共同记忆已有来源说明、可选原文快照，区分待核实／有效／过时 | 返回可核对的记忆编号，复用依据；不把相似度当成事实可信度 |
| 语音操作 | 固定句式触发共同记忆保存／修改，播报归属与范围后口头确认 | 第一阶段保持原流程；自然语言工具调用列为第二阶段 |
| 诊断 | 每轮识别、检索、模型、播报等阶段和耗时 | 补充检索策略、候选数量、无结果原因、评测统计 |

两个需要覆盖的问题：当前检索可能选入重合度为零的记录；共同记忆的状态优先排序可能让不相关的有效记录排在相关的待核实记录前面。新方案须明确“相关性”和“核实状态”各自的作用。

## 3. 分工与第一阶段边界

| 负责人 | 具体负责 | 交付责任 |
|---|---|---|
| 算法协作者 | 数据标注规范、检索基线、向量模型比较、混合检索、无结果门槛、效果与资源评测 | 可复现的检索模块、评测脚本、结果报告、局限说明 |
| 项目开发方（现有开发工作流） | 服务接口、权限过滤、索引更新触发、来源回填、语音及网页接入、诊断、回归验证 | 保持原业务规则，完成端到端集成及回退开关 |
| 产品负责人／实际用户 | 提供脱敏资料和真实问法，确认哪些记录属于正确答案，处理标注分歧 | 场景清单、标准答案及真实使用验收 |

第一阶段包含：共同记忆查询、数据集、基线对比、无答案处理、索引更新与失效、可配置启停、Mac 集成验证。

第一阶段不包含：自动保存／修改／删除记忆、自动分配权限、全面训练模型、声纹模型重训、机器人运动、开发板 NPU 适配、公网部署。个人记忆检索可在共同记忆验收后复用同一模块，不作为第一阶段阻塞项。

## 4. 具体任务与执行顺序

### M0：建立可比较的评测基线

- 用虚构或经授权脱敏的家庭／团队资料制作测试库，保留事件日期、记忆状态、归属及访问范围。
- 建议第一版 200 个问题，约 120 个用于开发、80 个作为冻结验收集。按来源事件／资料分组划分，不能把同一事件的近似问法分到两边后当成独立测试。
- 验收集至少包含 40 个有答案、20 个无答案问题，另覆盖至少 20 个权限／状态／更新情境；情境标签允许重叠。
- 每题标注：用户与空间、当时可见的记录、问题、正确记忆编号、无答案原因或需澄清点、预期状态提醒。不能只给问题和一段标准回答。
- 覆盖同义问法、人名／活动别称、时间模糊、重复记录、相互矛盾、待核实与过时、个人与团队隔离、其他家庭资料不可见等情况。
- 跑出现有实现的原始结果，冻结代码版本、数据版本和评分规则。门槛只能在开发集调整，验收集不用于反复调参。

交付：数据格式说明、脱敏样例、冻结划分、现有实现的基线报告。标注不一致的题由产品负责人裁定或明确标为有歧义。

### M1：实现三组可比较的检索方案

- A：现有字面匹配，保留原行为用于测量基线。
- B：字面检索加相关性门槛，修正“没有匹配也填入记录”的问题。
- C：字面检索＋语义向量召回＋结果融合。重新排序模型可作为后续实验项，只有效果收益值得额外开销时才启用。
- 模型先用现成方案。Qwen3-Embedding-0.6B 可列为候选，最终选择依据本项目中文资料的命中效果、Mac 耗时、内存和离线可用性，而非只看公开榜单。
- 人名、金额、日期等精确信息保留字面匹配能力；“上次”“周末”等时间表达应结合事件日期与程序提供的当前时间，不能仅凭向量相似度猜测。
- 没有足够相关记录时返回空结果；存在无法唯一确定的活动或互相冲突的候选时返回需澄清或多来源结果，不擅自决定哪条是真的。

交付：同一数据与权限范围下 A／B／C 的比较、推荐参数及放弃其他方案的理由。不要求更换现有对话模型。

### M2：接入现有服务及索引生命周期

- 通过项目服务端传入已授权的候选记忆；算法模块不负责登录、成员角色或权限决策。
- 原 SQLite 是事实主库。向量只是可重建索引，删除索引不能删除记忆，索引缺失也不能阻止服务启动。
- 首次建立索引后，支持新增、正文修改、删除、状态和成员权限变化。查询时使用当前授权范围和当前版本，不依赖过期索引中的权限副本。
- 缓存键至少区分个人／共同记忆、所属档案／空间、记忆编号、版本或内容哈希，以及模型版本与向量维度。修改模型时重建或隔离旧索引。
- 如果索引落后于主库，该条先重算、跳过或走有门槛的字面回退；不返回旧正文，也不把已撤销权限的内容放进模型上下文。
- 增加取消、超时和错误回退，向量服务失败不得触发整库回填或越权降级。回退策略必须在诊断里可见。

交付：新增／修改／删除／撤权后的集成演示、重启与索引重建验证、功能开关及回退说明。

### M3：验收与移交

- 冻结参数后运行验收集，报告各类问题的结果、失败样例和原始分子／分母。
- 同时测检索本身与最终回答；区分“没找到正确记录”和“找到了但回答说错”，不能只看最后一句话像不像。
- 在 Mac 演示文字问答，再接现有语音入口。语音转写错误单独分类，不拿语音录入失败混算检索命中率。
- 提供明确的后续清单：哪些问题需要更多数据，哪些可通过工程修复，哪些才需要微调或更复杂模型。

## 5. 怎么和现有代码对接

### 5.1 现有接入位置

以下均为仓库内已有路径；函数名已按当前代码核对。

| 位置 | 现有职责 | 建议改法 |
|---|---|---|
| `yiban/memory/shared_memory.py` → `SharedMemory.question_context(...)` | 验证账号／空间、筛选可见记忆、选择上下文、返回 sources 和 guard | 保留权限和状态筛选，用新模块替换排序及相关性筛选；保持返回字段兼容 |
| 同文件 → `SharedMemory.validate_answer(token, guard)` | 回答交付前复核账号、空间版本及权限 | 必须保留，不能因为前面过滤过就删除 |
| `server.py` → `shared_answer(...)` | 无来源时直接提示；有来源时调用模型，并返回 sources | 接住空结果；若新增需澄清结果，在调用模型前明确处理 |
| `yiban/memory/shared_voice.py` → `validate_query(...)` 与语音处理流程 | 复核会话取消状态；控制保存／修改的预览与确认 | 查询继续共用 shared_answer；保留会话校验及原确认流程 |
| `yiban/memory/shared_evidence.py` | 原文快照和摘录位置、访问控制 | 按已选记忆编号读取依据，不让算法编造原文；整份原文继续执行原权限 |
| `yiban/memory/memory_store.py` → `MemoryStore.context(identity, query)` | 个人档案及记忆上下文 | 后续复用检索模块时，仍保留个人身份上下文及档案隔离 |
| `yiban/settings.py` | 默认值、配置合并、字段校验、项目根路径 | 新增检索配置需同时更新默认值与严格校验；目前没有检索配置块 |
| `yiban/conversation_diagnostics.py` | 阶段及耗时记录 | 扩展细分信息时同步后端允许字段、网页展示和测试，避免被现有白名单丢弃 |

共同记忆推荐接入链路：

```text
语音转文字／文字问题
        ↓
原服务验证账号、空间、成员角色与可见范围
        ↓
按查询用途筛选状态，取得本轮授权候选及版本快照
        ↓
新检索模块：字面匹配＋语义召回＋相关性门槛
        ↓
服务端按编号回读当前记录，检查版本、权限并补齐来源
        ↓
无结果 → 明确说明没有相关记录
有歧义 → 澄清或同时说明多条记录的差异
有依据 → 原模型生成回答，保留 sources 与状态提示
        ↓
原 validate_answer／语音会话校验 → 网页与语音输出
```

pending 可以作为待核实资料返回，但不得表述为已确认事实。outdated 默认不作为当前安排的依据，只有明确查询历史时纳入。先满足内容相关性，再决定如何表达核实状态，避免让“有效但无关”的记录挤掉相关内容。

### 5.2 拟新增模块与接口约定

以下是建议接口，需要在 M0 结束时由双方确认；当前代码尚未提供。

建议新增 `yiban/memory/retrieval.py`，对接方通过构造参数注入实现，便于替换和测试。先以进程内 Python 模块交付，暂不要求独立 HTTP 服务。

```python
retrieve(query, candidates, *, top_k=5, cancel=None) -> RetrievalResult
```

输入候选由服务端生成，不能直接相信浏览器提交的记忆编号或权限。建议字段：

```json
{
  "id": "虚构记忆编号",
  "namespace": "shared:虚构空间编号",
  "version": "服务端映射的版本标识",
  "content": "10月团队自然观察活动由李老师讲解。",
  "status": "valid",
  "event_date": "2026-10-18",
  "content_hash": "服务端计算的正文哈希"
}
```

共同记忆的 version、个人记忆的 revision／内容哈希由对接层统一映射；个人记忆没有共同记忆的状态字段时，不虚构 valid 状态。上述样例只用于说明共同记忆输入。

建议返回：

```json
{
  "decision": "found",
  "hits": [
    {"id": "虚构记忆编号", "version": "服务端映射的版本标识", "score": 0.82}
  ],
  "reason_code": "relevant_candidates",
  "strategy": "hybrid",
  "elapsed_ms": 120
}
```

- decision：found、no_match 或 ambiguous；no_match 必须返回空 hits。ambiguous 用于问题本身无法确定目标，不是分数接近就必然追问。
- score 只是该实现的排序分值，不直接解释为“82% 正确”或与其他模型的分数横向比较。
- 输出 id 必须属于本次授权候选，版本必须一致；服务端仍做复核，不信任算法返回的额外编号。
- 返回候选编号与诊断信息，不直接拼接最终回答、不写记忆、不调用保存／删除接口。
- 来源正文、原文引用与可见范围由原服务回填。没有保留原文依据的记忆只能引用现有记忆及来源说明，不能补造原文。
- 对候选内容中的“忽略之前规则”等文字只作待检索资料处理，不作为指令执行。

### 5.3 配置、索引与部署约定

拟增加的配置至少包括：是否启用、检索策略、模型位置、top_k、相关性门槛、超时和索引位置。字段名与默认值在接口确认时固定，不能直接把未经支持的配置写进现有设置。

模型放在被忽略的 models/；索引建议放在 data/retrieval/，同样属于本机数据。代码中记录模型名称、版本／修订号、维度和预处理方式。提交依赖及安装说明，不提交模型权重、向量、真实资料、个人数据库或密钥。

现有数据默认留在本机；不得为调试方便把原始记忆发送给外部向量服务。若将来选云端方案，需另行明确资料范围、用途及用户同意，不属于本任务的默认授权。

## 7. 怎么验收

以下数值是第一版建议目标，不是已有成绩或性能承诺。M0 基线完成后一起确认；如需调整，应先记录理由并冻结新标准，不能见到测试结果后再降低门槛。

| 检查项 | 建议通过标准 | 如何检查 |
|---|---|---|
| 正确记忆是否找得到 | 验收集有答案问题 Hit@5 ≥ 90%；每题前 5 条至少有一条人工标注的相关记录 | 同一冻结集比较 A／B／C；同时报告逐类结果与分子／分母 |
| 多条依据是否找全 | 多证据问题另报 Recall@5，即前 5 条覆盖多少条必需依据 | 不用单条命中掩盖需要多条证据的问题 |
| 相比旧方案是否进步 | 语义改写问题优于原基线；若原基线已高于目标，新方案不能以达标为由接受明显退步 | 展示原问题、正确记录及各方案排名；统计小样本的不确定性 |
| 没有答案时不乱找 | 无答案集错误返回“有匹配”的比例 ≤ 10%；最终回答中无依据的事实陈述单独人工检查 | 至少 20 个无答案用例，避免与拒绝越权混为一类 |
| 权限和数据隔离 | 固定安全用例中越权候选、模型上下文泄漏、引用泄漏均为 0 | 覆盖其他档案、其他空间、指定成员、public_only、检索后撤权 |
| 未确认写入 | 本次查询功能不产生记忆写入；现有保存／修改确认测试全过 | 对比数据库、检查取消／确认过期／角色限制 |
| 状态与原文依据 | 固定用例中，待核实不当成已确认，过时不当成当前安排；引用可回到实际存在的记录／原文 | 包含缺失原文、重复与矛盾记录，逐条人工核对 |
| 索引一致性 | 新增可查；修改后不返回旧正文；删除和撤权立即阻止交付旧内容 | 故意制造旧索引、并发修改及跨账号缓存场景 |
| 检索速度 | 在双方记录配置的 Mac、1000 条候选、预热后建议 p95 ≤ 800 ms | 至少 200 次查询；分别报告冷启动、缓存命中／未命中；不含 ASR、对话模型或 TTS |
| 资源占用 | 报告模型加载后的增量常驻内存、峰值内存、索引大小与初次建库耗时 | 先测量，再根据实际 Mac 可用资源确定上限；不能冒充开发板结果 |
| 异常与取消 | 模型缺失、超时、索引损坏、用户取消时有明确结果；不扩大资料范围 | 可回退至有门槛的字面检索或返回暂不可用，不挂死服务 |
| 现有功能回归 | 项目统一测试通过，无未说明的跳过或新增失败 | 在完整本地环境运行 tests/run_all.py，并记录环境差异 |

安全用例中的“0”是该测试集合的硬门槛，不代表系统在所有真实场景下已经被证明零风险。Hit@5 与 Recall@5 的定义不同，报告中必须写清楚；原始分数、数据规模和样本量不可省略。

现有回归命令（已存在）：

```bash
./.venv/bin/python tests/run_all.py
```

将来新增的检索评测命令由交付方提供，目前不能当作已经可运行的入口。

## 8. 启动前需要哪些资料

- 项目开发方提供：已确认可用的代码版本、现有启动说明、接口说明、虚构的权限与记忆样例；无需提供个人数据库和 API Key。
- 产品负责人提供：20～30 个最常遇到的问题作为种子、哪些回答算正确、是否允许追问，以及必须优先解决的使用场景。
- 算法协作者提供：擅长方向、可用 Mac／GPU 环境、可投入时间；先评估样例和基线，再估工期。
- 双方共同确认：第一阶段仅做共同记忆查询、冻结验收集、性能测试机器、数据使用范围、代码评审人和交付方式。

按 M0 → M1 → M2 → M3 验收推进，不先承诺固定天数。每个阶段都留下可运行成果，避免只交一份 Notebook 或一张效果截图。

## 9. 第二阶段可以做什么

第一阶段通过后，优先让个人记忆复用同一检索能力；再做更自然的共同记忆语音操作。

第二阶段可让模型提出“查询／保存草稿／修改预览”的工具请求；程序仍校验身份、权限、参数和版本，写入前继续播报归属及可见范围并取得确认。涉及修改对象不唯一时先澄清，不依靠模型自选记录直接覆盖。

工具调用的业务接口、确认状态机、取消、重试次数和失败恢复由项目开发方负责；算法协作者可协助意图理解、参数提取及工具选择评测。通用自主 Agent、自动长期运行和公网部署不与第一阶段绑在一起。

## 10. 如果算法朋友不参与，我们能不能做

可以完成第一阶段可用版本。现有数据库、权限、原文依据、语音链路和测试基础已经具备，我们可以用现成向量模型实现算法模块及工程接入，不必等专家训练新模型。

建议自行实施顺序：先建立测试题和基线 → 加相关性门槛及空结果处理 → 接现成向量模型做混合检索 → 补版本／权限／索引一致性 → 跑评测和语音验收。

AI 开发助手可以协助设计接口、编写与调试代码、生成评测工具、分析失败样例和整理报告；产品负责人仍需确认真实答案、业务取舍及现场体验。模型效果要通过实测建立，不能仅凭代码和提示词保证。

算法专家的优势主要体现在系统化评测、排序与阈值调优、复杂歧义分析和必要时的领域微调。若后续目标变成远场声纹、多人重叠说话、回声消除或板端量化加速，应另设专项任务并安排对应专业与硬件验证资源。
